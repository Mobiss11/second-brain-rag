# second-brain-rag

Каркас второго мозга: база знаний на markdown, поиск по смыслу и ответы модели
только по найденному. Без выдумок: если в базе нет ответа, система говорит об
этом и передаёт вопрос человеку.

Сделан как минимальный рабочий пример, который можно развернуть за 15 минут и
дальше адаптировать под свой проект. Не фреймворк, не SaaS, без лишних слоёв.

## Из чего состоит

```
knowledge/*.md      база знаний, блоки разделены строкой ---
rag/chunking.py     чтение файлов и нарезка на блоки
rag/embeddings.py   эмбеддинги через любой OpenAI-совместимый API
rag/store.py        Qdrant: локально файлом или сервером
rag/ingest.py       индексация базы
rag/query.py        вопрос -> поиск -> порог -> ответ модели
rag/judge.py        проверка черновика перед выдачей (опционально)
```

## Запуск

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env      # вписать ключи
export $(grep -v '^#' .env | xargs)

python -m rag.ingest --dry-run    # проверить нарезку, без сети
python -m rag.ingest              # собрать индекс
python -m rag.query "ваш вопрос"  # проверить ответ
```

Без ключей можно посмотреть, как режется база:

```bash
python -m rag.ingest --dry-run
```

## Настройки

Всё через переменные окружения, список в `.env.example`.

| Переменная | Что задаёт | Пример |
|---|---|---|
| `EMBED_BASE_URL` | адрес API эмбеддингов | `https://openrouter.ai/api/v1` |
| `EMBED_API_KEY` | ключ эмбеддингов | - |
| `EMBED_MODEL` | модель эмбеддингов | `perplexity/pplx-embed-v1-4b` |
| `EMBED_DIM` | размерность, должна совпадать с моделью | `2560` |
| `LLM_BASE_URL` | адрес API модели ответа | `https://ai.api.cloud.yandex.net/v1` |
| `LLM_API_KEY` | ключ модели | - |
| `LLM_MODEL` | имя модели | `gpt://<folder>/yandexgpt-5.1/latest` |
| `LLM_PROJECT` | project для Yandex Cloud, у остальных пусто | `<folder>` |
| `QDRANT_PATH` | путь локальной базы | `./qdrant_data` |
| `QDRANT_URL` | сервер Qdrant вместо файла | `http://127.0.0.1:6333` |
| `TOP_K` | сколько кусков отдавать модели | `4` |
| `MIN_SCORE` | порог релевантности | `0.35` |
| `JUDGE` | включать проверку ответа | `1` |

Примеры провайдеров:

- эмбеддинги: OpenRouter (`pplx-embed-v1-4b`, 2560), Yandex text embeddings,
  локальный `bge-m3` через Ollama или vLLM;
- модель: YandexGPT, GigaChat, DeepSeek, GLM, локальная Qwen или Llama.

Модель ответа и модель эмбеддингов независимы. Сменили модель эмбеддингов -
переиндексируйте базу целиком, старые векторы несовместимы.

## Как адаптировать под свой проект

1. Заменить `knowledge/example.md` своими файлами. Один блок = один факт или
   один вопрос-ответ, 300-800 знаков, разделитель `---`.
2. Заменить `SYSTEM` в `rag/query.py` на свою роль и правила.
3. Прогнать `--dry-run`, проверить, что нарезка осмысленная.
4. Собрать индекс, задать 20-30 реальных вопросов, посмотреть, что находится
   и что уходит в отказ.
5. Подобрать `MIN_SCORE` на своих вопросах: слишком низкий - отвечает на всё,
   слишком высокий - отказывается там, где знает.
6. Включить `JUDGE=1`, когда пойдут ответы людям.

## Принципы, на которых это держится

- Знания лежат в файлах, модель их не помнит и не должна.
- Ответ строится только по найденному контексту.
- Цифры, цены, сроки берутся дословно из базы.
- Нет контекста или скор ниже порога - передаём человеку.
- Модель ничего не додумывает. Это правило в промпте и в коде одновременно.

## Чего здесь нет

- Расписания и автоматизации по cron.
- Загрузки PDF и офисных файлов: только markdown. Для документов нужен
  отдельный извлекатель.
- Векторного гибрида с полнотекстовым поиском. Для точных номеров и артикулов
  его стоит добавить.
- Интерфейса. Это ядро, обвязка под бота или сайт делается отдельно.

## Данные и 152-ФЗ

- Сервер, база и логи - в РФ.
- Модель и эмбеддинги - российские или локальные, если в базе персональные
  данные.
- Ключи только в `.env`, `.env` в `.gitignore`.
- В базу не класть лишние персональные данные. Если база про клиентов, сначала
  обезличивание, потом индексация.
